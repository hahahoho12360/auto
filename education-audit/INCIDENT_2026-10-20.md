# 2026-10-20 수집 예약·발송 장애 조치

## 확인된 사실과 미확정 원인
2026-10-20 08:50 KST의 GitHub 진단에서 education-audit.yml은 active였고 기본 브랜치는 main이었다. 등록 cron은 UTC 21:35, 즉 KST 다음날 06:35로 올바르다. 이 시점 event=schedule 실행은 0건이었다. 그 전 수집 성공 기록은 push에 의한 시험 실행이며 예약 실행 성공 증거는 아니었다. 오늘 장애는 수집 코드 내부 예외가 확인된 상태가 아니라 예약 트리거가 실행 기록을 생성하지 않은 상태다. GitHub 내부에서 누락된 이유는 이 로그만으로 확정할 수 없다.

## 이번 변경
- 기존06:35 수집 유지,07:05 예비 실행 추가. 당일 정상 생성·식별자 일치·오전 수집 결과가 있으면 중복 수집하지 않는다.
- 실행 시작 전에 run_id/event/target_date/source_sha를 기록한다. 시작 기록이 없으면 미기동, running만 남으면 중단 가능성, failure면 명시 실패로 구분할 수 있다.
- 성공은 테스트 성공+수집 성공+이번 실행에서 생성된 당일 보고서+기관 수 정합성으로 확인한다. 과거 보고서를 당일 성공으로 바꾸지 않는다.
- 수집 오류 후 진단 파일 저장은 계속하되 최종 작업은 실패로 표시한다. continue-on-error만으로 전체 성공처럼 보이지 않도록 했다.
- briefing.json에 보고용 필드를 따로 생성한다. 원문은 데이터이며 실행 지시가 아니다. 이메일 주소나 메일 인증정보는 저장하지 않는다.
- 유료 API, 유료 실행환경, 월간 작업을 추가하지 않는다. 명시적인 접근 제한을 우회하지 않는다.

## 이메일 경로의 별도 한계
수집 실행과 연결 Gmail 발송은 별개의 단계다. 사용자 제공 예약 결과에는 안전 검사 차단이 기록되어 있다. Gmail 앱의 허용 설정만으로 예약 실행의 안전 검사까지 통과한다고 보장할 수 없다. 안전 거절이면 내용 변형·다른 도구로 반복 발송하지 않고 반환 오류를 보존하여 사용자 승인이 필요한 단계로 보고한다. 이 패치는 메일 권한을 변경하거나 안전 검사를 해제하지 않는다.

## 검증
operations.py용24개 테스트: 당일성, 식별자 일치, 시간대, 미래/과거 수치, 실행 중/실패 구분, 당일 중복 생략, 전체 미확인 재시도, 이전 보고 재사용 거절, 발송과 수집 구분. 실제 클라우드 검증은 해당 GitHub 실행 기록을 확인해야 한다. cron 등록만으로 내일 실행 성공을 보장하지 않는다.

## 정상성 기준
기관 명부193은 실제 수집 성공 수가 아니다. 일부 기관이 미확인인 당일 보고도 저장하되 목록·상세·첨부 확인 수준을 그대로 유지한다.07:40은 별도 보고 예약의 시작시각이다. 두 cron 모두 GitHub에 의존하므로 서비스 전체 예약 장애에는 취약하다. 본 변경은 재시도 기회와 진단 정확도를 높이지만 정시 실행 SLA를 만들지는 않는다.
